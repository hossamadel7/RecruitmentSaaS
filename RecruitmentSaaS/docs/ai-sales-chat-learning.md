# Learning material from CRM chats

The owner requested using all chats and confirmed the source is this CRM's WhatsApp inbox. This increment implements **local corpus preparation**, not a fine-tuned model, automatic self-learning or a provider upload. Actual CRM history has not been extracted in this development session. No provider key is configured by this change. No production configuration or database was modified.

## What is implemented

`AiChatLearningService` pages through stored messages in explicitly selected WhatsApp accounts. It is not restricted to AI-assigned leads, open chats or the last twenty messages: closed, unassigned and older stored chats are included. Administrator-only `POST /api/ai-chat-learning/prepare` requires normal authentication/CSRF, enabled foundation, enabled chat preparation, a server-approved account list and a separate server-side pseudonym secret of at least 32 UTF-8 bytes. It defaults off. `GET /api/ai-chat-learning/status` returns no secret. The later [fact-review screen](ai-sales-chat-fact-review.md) calls this preparation path and proposes one owner-reviewed question at a time. There is no external uploader or training worker.

The request shape is `{ "accountId": "<guid>", "pageSize": 100 }`. Maximum page size is 300 messages. Continue with the returned `nextAfterMessageId` and unchanged `snapshotBefore` until `hasMore=false`; continuation without its original boundary is rejected. Iterate all explicitly selected accounts to cover the requested CRM corpus. Paging uses PostgreSQL UUID ordering, not chronological ordering. Reassemble conversations and sort by timestamp/reference before reviewing context or forming training examples. Fixed time boundaries exclude newly created messages but are not an immutable database snapshot: edits/deletions during preparation can affect results. Run a consistent sanitized snapshot or account for source changes when freezing an evaluation/training dataset. Missing/deleted history cannot be reconstructed.

The legacy CRM has no complete multi-tenant account resolver. The approved account list is the explicit deployment boundary, not proof of full legacy tenant isolation. Administrators must select only the intended organization's accounts. Voice transcripts additionally require the configured tenant. Do not infer an account belongs to a tenant just because both records exist.

## Privacy and review

The result masks common email addresses, links, long numeric identifiers (including Arabic digits), and known contact/lead/sender names. Conversation references use HMAC pseudonyms instead of raw chat/customer IDs. Original message GUIDs remain **internal review references**, not external training identifiers. Raw provider IDs, media URLs, contact phone fields, passports, lead records and raw transport error bodies are not exported by this preparation path. Response caching is disabled. Each preparation request writes a text-free account-level audit entry.

This is partial masking, **not guaranteed anonymization**. Unknown names, addresses, short identifiers, embedded identifiers, or identifying narratives can remain. Every item requires manual privacy review before reuse outside its original CRM context. Keep prepared output restricted, set a retention/deletion policy, and remove internal references before any provider dataset upload. Never upload this API output directly as a training dataset.

All rows are marked `trainingReady=false`. `candidateForReview` means only that text is present and its source/status is eligible for examination. It is not approval or a quality score. AI/system outgoing messages are marked unsuitable as human training targets. Unconfirmed/failed outgoing messages are also unsuitable; Business App messages without a staff author need authorship review. Customer questions can inform examples but cannot be used as assistant answers. Old fees, salaries, travel dates and vacancy claims remain historical data and are never automatically published to current knowledge. Separate Turkey and Saudi topics before applying examples to the Turkey agent. Conversion and no-show labels are not inferred from chat text or current lead status.

Audio is represented only by an existing staff-reviewed transcript matching its conversation/tenant. Group transcripts may occur across multiple recording references; deduplicate the flagged voice group before building examples. Unreviewed audio and other media get review flags and no inferred text. The service downloads or transcribes no historical recordings. Complete approved transcription/interpretation separately if the owner wants media content included in the learning material. No customer-data payload is sent to an AI provider in this increment.

## From the whole corpus to useful learning

1. Prepare every selected account's available history locally, then review privacy, speaker attribution and conversation context.
2. Group and deduplicate conversations/voice groups. Separate Turkey content, outdated offers, mistakes, unsupported promises, opt-outs and failed sends. Consider the whole corpus, but do not turn every historical answer into an approved assistant target.
3. Approve reusable Egyptian Arabic sales techniques as Playbook examples. Verify and publish current business facts through the existing knowledge workflow; customer/staff chat assertions alone do not verify current fees, contracts or vacancies.
4. Split reviewed conversations into training and held-out evaluation groups at conversation level. Build context/approved-answer examples and assess them against the Turkey cases. Do not let fragments of the same conversation appear in both groups.
5. Decide whether reviewed retrieval/playbooks suffice or whether actual model fine-tuning is needed. Provider-specific training dataset generation, upload, fine-tuning jobs, model selection, held-out semantic evaluation and deployment are **not implemented here**. They require secure provider setup and a reviewed dataset. No trained model can be reported until a real job has completed and its behavior has been tested.

This first increment makes the requested history accessible for controlled preparation without silently teaching the assistant old or incorrect claims. It does not make the agent learn automatically from every new chat.

## Verification

Isolated tests exercise whole-history pagination, account separation, masking, local-review status, source-message preservation, text-free auditing, closed/unassigned historical chats, AI/system and failed send exclusion, unreviewed media flags, disabled/unselected account gates, continuation validation, administrator authorization and CSRF. Tests use disposable fixture databases with fictional customers; there was no actual corpus export. The main build retains its five pre-existing warnings. All **nine targeted preparation tests passed**. The broader run passed 107 cases and found one invalid test seed (it reused a contact/account pair despite the CRM's uniqueness constraint); changing that seed to a separate fictional contact fixed the scenario, verified in the targeted run. No application behavior was changed for that fixture repair. The dedicated local database was stopped after validation.
