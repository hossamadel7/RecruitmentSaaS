# Automatic replies after manual assignment

The owner requested an AI identity named **مصطفى زكي — مساعد AI** that replies without per-message approval on any conversation newly assigned to it. The feature was released on 19 October 2026 for the Bakar, Mekky and Sherif accounts. Each identity remains bound to its own account and team. There is no human login or fabricated human reviewer. The customer-facing assistant retains its virtual-assistant identity.

An administrator selects a conversation and assigns the matching Mustafa identity. New assignments after the configured activation time enter Assisted control, including conversations previously collecting intake data. The worker debounces incoming messages, prepares a reply, authorizes it as `AutomaticallyApproved`, and sends it through the existing durable dispatch flow. The page identifies automatic mode and refreshes draft status. Monitoring remains available through the inbox.

Old assignments are not activated retroactively. To use an already assigned conversation, release it to the human workflow and explicitly assign it again. Staff takeover, a paused agent, changed ownership, revoked release, stale context, expired knowledge, quotas or an expired WhatsApp reply window prevent sending. Actual handoff/stop drafts remain for staff handling. An uninterpreted voice note can request written clarification automatically.

`AiSalesEngine:AutoReplyEnabled`, `AutoReplyAnyAssignedConversation`, `AutoReplyAgentIds` and `AutoReplySinceUtc` authorize the assignment-based path. `AiSalesDispatch:AutomaticEnabled`, normal release approval and approved accounts independently gate transport. Default configuration leaves automation disabled. Exact-conversation pilot settings continue to govern ordinary staff-requested drafts and reviewed sends. The automatic service bypasses that pilot list only for explicitly permitted agents with a new active assignment in the configured tenant. Other agents/accounts remain outside the release.

There is one persistent request key per incoming message and ownership version. Generation and dispatch use database advisory locks. Uncertain/interrupted transport is never automatically repeated. Automatic records have no human requester or reviewer; migration `20261019005122_AiAutomaticReplyAttribution` allows a nullable draft requester and refuses rollback while unattributed automatic drafts remain. Ordinary authenticated APIs still require their existing roles and CSRF validation.

Validation: 18 focused PostgreSQL tests passed, including new assignments outside the pilot list, exclusion of old assignments and unapproved agents, one send per turn, uncertain outcome handling, takeover during generation, automatic assignment bypassing legacy intake, existing reviewed dispatch, HTTP authorization/CSRF and genuine stop/handoff routing. All transports/providers were synthetic. Model/migration consistency, JavaScript syntax and publication passed. No live customer was contacted by deployment verification.

Installation included a full database recovery dump and prior code/configuration copies. Before/after checks preserved rows and original-column digests across all 99 existing tables. Current knowledge was preserved for Bakar/Sherif and the same owner-approved pack was published for Mekky with system attribution and the original validity interval. The agents allow up to 50 active assignments each; existing shared daily draft/send budgets remain in force. Live health, three active identities, effective release settings and absence of automatic-worker errors were checked. Actual real-customer acceptance remains an owner-supervised test.
