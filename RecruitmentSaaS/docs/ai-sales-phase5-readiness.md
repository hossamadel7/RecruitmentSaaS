# Phase 5 — local evaluation and supervised-pilot readiness

This increment supplies an executable synthetic replay runner, bounded concurrency checks, an admin operational dashboard and a release evidence worksheet. It does **not** qualify a live pilot or implement automatic customer dispatch/weighted AI rotation. Actual business facts, approved representative conversations/audio, real-provider evaluation, staging rehearsal and release decisions remain outstanding.

## Local replay runner

`Tests/ReplayRunner` is a separate executable referencing the disposable test fixture and the production draft services. It is excluded from the application project and never loads application settings, registers WhatsApp transport/hosted workers, or constructs OpenAI/Meta clients. The fixture accepts only `127.0.0.1:55439`, user `phase1_test`, and creates/drops a unique database. An existing production or staging database is not accepted.

From the workspace root in PowerShell, with the dedicated test cluster running:

```powershell
$env:AI_SALES_TEST_DATABASE='Host=127.0.0.1;Port=55439;Username=phase1_test;Database=postgres'
dotnet run --project Tests/ReplayRunner/ReplayRunner.csproj -- 'C:\Users\hadel\source\repos\RecruitmentSaaS\RecruitmentSaaS'
```

The runner reads `docs/evaluation/synthetic-sales-cases.json`, requires its synthetic-only marker and known bounded schema, and rejects playbook-as-fact citation allowances. It creates isolated tenants/accounts for each scenario, runs all 16 cases three times, and then runs eight independent sessions concurrently. The concurrency burst is an in-process/local PostgreSQL probe across separate synthetic tenants, not representative production traffic or a shared-tenant provider admission test. A separate regression test holds two fake provider calls pending in one tenant and confirms that a third generation is rejected before a provider call or reservation.

Checks cover preserved known/unknown customer fields and reviewed memory, scoped currently approved retrieval, retired facts, identifier redaction, expected provider/local-policy path, draft state/intent, citation allowances/requirements, review flags, request replay, no added outgoing messages or unauthorized CRM changes, and deterministic takeover with stale text discarded and simulated usage retained. Customer refusal/person-request cases exercise the local draft fallback in a directly seeded Assisted conversation; this does not replace the separate webhook takeover checks. Audio remains uninterpreted unless separately staff-reviewed by Phase 3.

The fake provider returns a deliberately generic review-only reply. Its replies are not real model outputs and are not scored for natural Egyptian Arabic, objection handling, factual entailment or commercial usefulness. A passed injection scenario establishes context/action constraints under the fake provider, not model resistance to injected text. Semantic assessment remains `not_run`, and the human score sheet stays blank. Repeating a deterministic fake does not measure model variability.

Output is `docs/validation/phase5-synthetic-replay.json` (or an explicit second absolute output-directory argument). It records case-file SHA-256, fixture version, prompt-version reference, per-case structural checks/path/state/reply/citations, simulated token values, three repetitions, concurrent probe and elapsed time. Latency includes seeding and database checks and cannot serve as a production SLO or actual API latency. Any failed structural run returns a nonzero exit code. All database changes belong to the fixture and are removed afterward.

## Operational dashboard

`/AiSalesAdmin` now includes a manual-refresh operational panel backed by `GET /api/ai-sales-operations` (Role 1 only). It exposes aggregates for the configured deployment tenant, without customer text, phones, transcript bodies, secret keys, raw webhook payloads or individual provider error messages. Unscoped webhook metrics are deliberately absent; monitor the legacy deployment queue through its existing operational tooling.

The panel shows current states of drafts, voice turns and bookings created in the last 24 hours; local-policy drafts; sums of reported usage with unknown-record counts; voice attempts today in UTC; completed-draft duration p50/p95 using the newest 1,000 samples; outstanding drafts older than two minutes; due Pending/Processing voice work older than ten minutes; reviewed transcripts with no probability indicator; and bookings with verified visit references versus unknown attendance. These are read-only sequential aggregates, not a transactionally consistent billing snapshot.

Draft latency includes local-policy, failed and stale outcomes, measured from draft reservation to completion. It is not a separate provider-latency metric. An empty sample stays null. Truncation is displayed. Voice token/second totals describe the latest saved result for each attempted recording, not all prior retry charges. The dashboard counts UTC-day attempts without a corresponding latest reported result, including prior ambiguous attempts. Reporting dimensions remain explicit: some providers return tokens, others seconds, and missing values do not become measured zero. Monetary cost is unknown; no pricing estimate is invented.

Migration history is read only. The disposable `EnsureCreated` database has tables but no applied migration history, so the dashboard correctly calls that history unverified. Applied migrations alone do not prove that an existing staging schema or restore process is safe. There is no new migration in this increment.

Configuration, approved-entry counts and absence of stale jobs are narrow checks. They do not prove business accuracy, consent, acoustic accuracy, privacy compliance, capacity or model quality. Live-pilot qualification remains false and automatic release unavailable. The dashboard is informational, not a new admission controller: existing separately configured manual draft/voice/booking features keep their prior gates. No override or automatic release endpoint was added.

## Required evidence before a supervised live pilot

Use [release-readiness-template.json](evaluation/release-readiness-template.json) and the existing evaluation score sheet. The blank worksheet does not grant approval and must not contain API keys or unredacted conversation data.

1. Business owner verifies actual branch details/hours, current fees/service terms, vacancies and policy references for the chosen account/team. Approve short, time-bounded facts and office policies in the application. Unknown fees, terms or salaries remain unknown; the fictional evaluation pack is never real company knowledge.
2. Establish approved external processing, permitted account/tenant scope, access controls, selective historical-data handling, deidentification, retention/deletion policy and permission for any real sample processing. Do not upload historical datasets or fine-tune automatically.
3. Rehearse the four additive migrations on a sanitized staging copy; verify compatible legacy reports/reception/admin edits, backup restoration and rollback. Validate webhook signature/retry handling, request idempotency, worker restart, takeover, failed-provider recovery, timeout costs and secrets handling. No production connection or migration was performed here.
4. In approved isolated staging, run real-model cases and representative authorized Egyptian Arabic/audio samples, including noise, numbers, opt-out, prompt injection and mixed media. Repeat model-backed cases three times and manually assess factual support, Arabic, context use and useful next step. Log model/prompt/knowledge versions, approved citations, actions and usage. Proposed criteria remain zero critical violations, at least 90% scenario coverage and median dimension scores of 4/5; get business acceptance before treating them as release thresholds.
5. Agree measured latency, failure and spend limits with the operator. Stage representative HTTP/webhook/SignalR/voice workload, connection limits, sustained bursts and outage/recovery behavior. Local fake-provider burst timings do not validate the observed daily WhatsApp traffic or the single voice worker's real throughput. Monitor aggregate metrics through authenticated access and existing infrastructure logs; never export customer bodies as monitoring labels.
6. Start a small, explicitly approved manual-assignment Shadow pilot within existing limits (default 20 draft reservations/tenant/UTC day, 100 voice attempts/tenant/UTC day, two concurrent draft generations and ten assignments per agent). Staff reviews facts, voice transcripts, replies and booking evidence. Staff sends via the existing inbox; sending takes over conversation control. Resume only through the explicit authorized action when appropriate, after a new customer message. There is no automatic customer dispatch, copy-to-send workflow or rotation participation.
7. Record real verified bookings and matching reception visits separately from reviewer activity. Missing attendance remains unknown. Stop/disable provider processing on critical violations, rising failures, overdue work, privacy incidents or unexpected spend; take over affected conversations. Keep human handling available. Reconcile ambiguous paid attempts before deciding whether to retry.

## Rollback and later production work

Disable external draft/voice processing, automatic incoming voice queueing and new office bookings/reschedules; take over pilot conversations and resolve outstanding bookings/reminders with staff. Do not discard populated audit, transcript or booking evidence. Preserve additive tables and current ownership data while reverting a reviewed compatible code version, or use the separately rehearsed restore/data-migration plan. The new dashboard/runner need no schema rollback.

The later [reviewed text dispatch increment](ai-sales-reviewed-dispatch.md) adds a disabled-by-default, explicit administrator API, attempt budgeting, window checks, pending-send invalidation and virtual message authorship. It has no automatic worker, dispatch UI, templates or automatic uncertain-result reconciliation. Controlled weighted AI rotation and customer-facing automated dispatch remain further implementation/release work, including live mode/agent quotas, team-weighted rotation, attribution/commission handling and explicit release approval. The current two-mode agent identity (Disabled/Shadow) cannot be declared production-eligible merely by completing a worksheet.
