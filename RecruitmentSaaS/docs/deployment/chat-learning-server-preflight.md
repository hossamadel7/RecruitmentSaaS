It contains seven conditional migration upgrades. It was generated offline using the design-time factory, which loads no deployment secrets or hosted workers. It is a review artifact, not evidence that the server is PostgreSQL, on that baseline, compatible with the current code or backed up.

First obtain the owner's server address/saved connection and use existing authorized access. Inspect the active deployment/code version and effective database type/target without printing credentials. Read migration history, compare the expected pre-AI schema and identify the organization's actual WhatsApp accounts and available message counts. Check the existing backup/restore and staging rehearsal evidence before proposing the database/code rollout. The empty historical baseline does not provision a fresh legacy database. Do not use the repository's destructive migration scripts.

If the confirmed target is not the expected PostgreSQL schema/baseline, stop and reconcile it; do not apply this SQL as a conversion or drift repair. Conditional migration history checks do not independently validate existing schema or replace a backup. The [14 October rehearsal](ai-backup-restore-rehearsal.md) restored a private production snapshot locally and verified all seven migrations preserve original data. No migration SQL has been applied to production.

After an authorized rollout, configure a stable deployment tenant, selected account IDs and the separate pseudonym secret through the deployment's existing secret/configuration mechanism. Keep external processing and customer dispatch disabled. Start the local extraction/review screen with a small batch, verify its source/account boundaries, then continue the approved histories. Ask the owner one question at a time and publish only their reviewed corrections. This review step needs no OpenAI key. Actual AI reply generation and model fine-tuning remain separate configuration/evaluation steps.
